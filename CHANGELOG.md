# Changelog

## 0.0.5
Тестовая сборка, шаг 2 плана: определение мира.

- **Команда `resolve <port>`**: порт → процесс игры → папка игры → открытый мир. Папка игры берётся из
  `--gameDir` (относительный считается от рабочей папки игры) или, если его нет, из рабочей папки
  (MultiMC, Prism). Открытый мир: занятый `session.lock`, иначе изменённый после запуска игры,
  иначе список кандидатов для вопроса.
- Порт ищется в таблицах IPv4 и IPv6: Java на Windows часто слушает двухстековый сокет.
- Если Windows не отдаёт командную строку обычным способом, она читается из памяти процесса,
  так же, как рабочая папка.
- **CLI для проверки без Porthole**: `world_backup_cli.exe --resolve <порт>`, `--resolve all`,
  `--resolve-pid <pid>`. В окне консоли кириллица выводится правильно без `chcp 65001`.
- Тесты: логика разбора аргументов, путей и выбора мира на C (38 проверок), необязательный дымовой
  тест под Wine с поддельной игрой (`tests/win/smoke.sh`).

## 0.0.4
Тестовая сборка: хелпер не остаётся сиротой.

- **Сторожевой таймер в хелпере.** Если 60 с не пришло ни одной команды с верным токеном
  (дополнение шлёт ping раз в 10 с), хелпер завершается сам. После выхода из лобби дополнение
  не получило в 0.0.3 ни одного события, и хелпер мог остаться висеть до перезапуска Porthole.
- **Диагностика:** раз в 30 с строка `alive` с ролью и состоянием хелпера. По ней видно, работает ли
  дополнение после выхода из лобби. Будет убрана перед 0.1.0.

## 0.0.3
Тестовая сборка: правильный признак лобби и сроки по часам.

- **Исправлено: хелпер работал вне лобби.** В Porthole 3.0.2 вне лобби роль `"idle"`, а не пустая
  строка. Сессией считается любая роль, кроме `""` и `"idle"`.
- **Исправлено: только что запущенный хелпер сбрасывался.** При загрузке дополнения Porthole вызывает
  `on_tick` пачкой (20 раз за 27 мс), а сроки считались в тиках. Теперь все сроки (ожидание ready,
  ping, pong, паузы перед перезапуском) считаются в секундах по `os.clock()`.
- **Устойчивость к порядку событий.** События применяются сразу, а роль ещё и опрашивается на каждом
  тике: если опрос расходится с событиями дольше 2 с, побеждает опрос. Так хелпер остановится,
  даже если Porthole не сообщит о выходе из лобби.
- Из диагностики убрано число участников: без разрешения `roster` функции `roster()` нет.

## 0.0.2
Тестовая сборка: диагностика сессии.

- **Канал `tcp_open` подтверждён** в Porthole 3.0.2: `send` и `close` вызываются как функции
  таблицы. Угадывание способа вызова убрано.
- **В лог пишется всё о сессии**: значение `role()` при загрузке, при смене роли и в конце сессии,
  число участников. В 0.0.1 хелпер стартовал без лобби, значит `role()` вне лобби не пустая;
  правильный признак лобби выберем по этим строкам.
- В лог пишутся запуск и остановка хелпера с портом.

## 0.0.1
Тестовая сборка, шаг 1 плана: каркас без бэкапа.

- **Хелпер `world_backup.dll`** запускается только внутри сессии лобби, один процесс на сессию.
- **Новый агент**: держит несколько соединений одновременно и выполняет каждую строку сразу.
  Агент из лабы читал соединение до закрытия, поэтому не работал с `tcp_open`.
- **Канал команд**: постоянное соединение `tcp_open`, проверка ping-ом, откат на `tcp_send`.
  Вкладка показывает, какой канал выбран.
- **Надзор**: ping раз в 10 с, перезапуск зависшего хелпера с нарастающей паузой.
- **Вкладка** считает размер текста до отрисовки и никогда не превышает лимит Porthole в 4096 байт.
- Тесты: протокол агента, юнит-тесты и сценарии Luau, проверка текстов. Воспроизводимая сборка.
